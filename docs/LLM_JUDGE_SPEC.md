# LLM-as-Judge Triage Layer — Specification & Design

**Status:** Design draft, not yet implemented.
**Audience:** Whoever picks this up for implementation.
**Scope:** A triage layer that sits between the existing detection engines
and the analyst. Ranks candidates, produces natural-language reasoning,
and is calibrated against the labeled ground truth already in the repo.

---

## 1. Executive summary

The dashboard already runs three unsupervised ML models (IsolationForest,
DBSCAN, LSTM), two deterministic rule layers, and six advanced threat
engines. Each produces its own signal. Nothing fuses them into a single
per-candidate verdict, and nothing produces a natural-language rationale.
The analyst pays the full cognitive cost of every false positive.

This spec adds one component: an **LLM-as-Judge** that receives one
candidate at a time (one IP, or one flow), sees every relevant signal in a
compact JSON blob, and returns a strict-JSON verdict with a category,
confidence, evidence list, and one-paragraph reasoning trace. Its output
re-ranks the queue the analyst sees and produces the summary the analyst
would have written anyway.

The Judge is calibrated via **Cohen's kappa** against
`attack_tests/ground_truth.json` — the labels are already exhaustive for
five real attack PCAPs, so no external calibration set is required. Kappa
becomes the single number that guards prompt drift.

**Non-goal:** the Judge does not act. `recommended_action: "block"` is a
suggestion for the analyst, never wired to a blocklist.

## 3. Problem statement

Three concrete pain points:

1. **No single verdict per candidate.** IsolationForest says "outlier
   score = −0.31, stability = 0.8"; DBSCAN says "cluster = −1"; the SYN
   rule says "scan_alert of type SYN"; the advanced engines each add their
   own tag. The analyst is the fuser.
2. **No natural-language reasoning.** The Model Diagnostics card exposes
   the hyperparameters; `docs/MODELS.md` explains what each model does; the
   analyst still writes the "why this IP is suspicious" paragraph by hand.
3. **No calibration signal.** Detection quality is measured per-layer
   (precision / recall / F1 against ground truth), but there is no
   single-number gauge that regresses when the fusion logic drifts. Adding
   a rule or tweaking a threshold has no obvious cost-of-drift signal.

---

## 4. Proposed solution

Insert one component in the pipeline: an **LLM-as-Judge** that receives
one candidate at a time, sees every relevant signal in a compact JSON
blob, and returns a strict-JSON verdict.

### 4.1 What a "candidate" is

Any entity flagged by **at least one** of:

- IsolationForest majority-vote anomaly (`iso_stability >= 0.5`)
- DBSCAN noise (`cluster == -1`) — subject to the 5000-IP cap
- LSTM temporal anomaly (bin error > `val_mean + 2σ`) attributed back to
  the IPs active in that bin
- Any deterministic rule (`scan_alerts`, `flood_alerts`, `amp_alerts`,
  `arp_spoofing_ips`, `arp_spoofing_macs`)
- Any advanced threat engine finding

The candidate identity is one of:

- **Per-IP:** an `ip_agg` row
- **Per-flow:** an `(src, dst, proto)` tuple, used only for advanced-engine
  findings that don't map cleanly to a single IP (e.g. beaconing pairs)

The default entity is per-IP. Per-flow candidates are enqueued only when
an advanced engine emits a flow-level finding.

### 4.2 What the Judge sees

A **compact JSON** blob, budgeted at 2–4 KB per candidate:

```json
{
  "candidate_id": "192.168.1.10",
  "kind": "ip",
  "session_context": {
    "duration_s": 71.2,
    "total_packets": 2020,
    "total_ips": 5
  },
  "features": {
    "mean_len": 60.0, "std_len": 0.0, "count": 1007,
    "burst_score": 1007.0, "unique_dsts": 1000,
    "syn_count": 1002, "rst_count": 0,
    "fin_count": 0, "null_count": 0, "xmas_count": 0
  },
  "ml_signals": {
    "iso_score": -0.31, "iso_stability": 1.0, "anomaly": true,
    "cluster": -1, "silhouette": null,
    "lstm_bin_flag_count": 0
  },
  "rule_signals": {
    "scan_alerts": [{"type": "SYN", "count": 1002, "unique_dsts": 1000, "ratio": 1.0}],
    "flood_alerts": [],
    "amp_alerts": [],
    "arp_multi_mac": false
  },
  "advanced_signals": {
    "beaconing": null,
    "dns_tunneling": null,
    "dga": null,
    "tls_anomaly": null,
    "fusion_score": null
  },
  "device_context": {
    "category": "unknown",
    "hostname": null,
    "oui_vendor": null
  },
  "enrichments": {
    "is_private": true,
    "reverse_dns": null,
    "asn": null,
    "baseline_seen_before": false
  }
}
```

Every field is optional except `candidate_id`, `kind`, `features`, and
`ml_signals`. Nulls / empty lists mean "not applicable."

### 4.3 What the Judge returns

Strict JSON — the response is rejected and retried if it fails schema
validation:

```json
{
  "verdict": "benign | suspicious | malicious",
  "category": "beaconing_c2 | dns_tunnel | dns_amp | port_scan | arp_mitm | syn_flood | benign_anomaly",
  "confidence": 0.0,
  "evidence_features": ["syn_count", "unique_dsts", "scan_alert.SYN"],
  "reasoning": "One paragraph, <= 400 chars, explaining the verdict.",
  "recommended_action": "monitor | investigate | block"
}
```

Constraints:

- `confidence` in `[0.0, 1.0]`.
- `evidence_features` references field names from the input blob (or
  dotted paths into it). Enforced only softly — used to render UI
  highlights, not for control flow.
- `reasoning` is a single string, no newlines, hard-capped by prompt.
- Failed schema validation: **retry once**, then drop the candidate from
  the Judge queue and log the failure. Never poison the scoreboard with a
  half-parsed response.

### 4.4 Categories — mapping to ground truth

| Judge category | Ground-truth attack |
|---|---|
| `port_scan` | `tcp_syn_scan`, `tcp_xmas_scan` |
| `arp_mitm` | `arp_spoofing` |
| `syn_flood` | `spoofed_syn_flood` |
| `dns_amp` | `dns_amplification` |
| `beaconing_c2` | (not in current ground truth — future) |
| `dns_tunnel` | (not in current ground truth — future) |
| `benign_anomaly` | any IP flagged by a detector but labeled benign |

This mapping is what makes Cohen's kappa well-defined against the current
ground truth. The `beaconing_c2` and `dns_tunnel` categories are declared
now so the prompt is future-proof.

## 5. Runtime behavior — end-to-end flow

The flow, at load time of one PCAP:

```
                +----------------------------+
                |  PCAP file (S1 or S2)      |
                +-------------+--------------+
                              |
                              v
             +----------------+---------------+
             |  tshark feature extraction     |    (cell 8, unchanged)
             |  -> ip_agg, dns_amp_per_src,   |
             |     arp maps, tcp flag counters|
             +----------------+---------------+
                              |
                              v
             +----------------+---------------+
             |  ML engines + rules + advanced |    (cells 12/16 + advanced
             |  -> ml_signals, rule_signals,  |     engines cell, unchanged)
             |     advanced_signals           |
             +----------------+---------------+
                              |
                              v
             +----------------+---------------+
             |  Candidate assembler           |    NEW
             |  - union of flagged entities   |
             |  - one JSON blob per candidate |
             |  - dedup by fingerprint        |
             +----------------+---------------+
                              |
                              v
             +----------------+---------------+
             |  Cache lookup (SQLite)         |    NEW
             |  - key: (fingerprint, prompt_v)|
             |  - hit -> reuse verdict        |
             |  - miss -> call LLM            |
             +----------------+---------------+
                              |
                              v
             +----------------+---------------+
             |  LLM call (strict JSON mode)   |    NEW
             |  - schema-validate response    |
             |  - retry once on invalid       |
             |  - drop + log on 2nd failure   |
             +----------------+---------------+
                              |
                              v
             +----------------+---------------+
             |  Ensemble scorer               |    NEW
             |  priority =                    |
             |    w1*anomaly_score +          |
             |    w2*judge_confidence +       |
             |    w3*category_weight +        |
             |    w4*threat_intel (opt.)      |
             +----------------+---------------+
                              |
                              v
             +----------------+---------------+
             |  Dashboard: re-ranked queue    |    NEW UI (Dash card)
             |  + inline reasoning trace      |
             |  + analyst verdict widget      |
             +----------------+---------------+
                              |
                              v
             +----------------+---------------+
             |  data/analyst_verdicts.jsonl   |    NEW audit log
             |  (agree / disagree / override) |
             +--------------------------------+
```

Key properties:

- **The LLM call is the only I/O-bound step.** Everything else is
  deterministic Python on already-computed DataFrames.
- **Cache is aggressive.** A candidate fingerprint = hash of the input
  JSON blob. Two identical blobs hit the same verdict. Fingerprint also
  includes the prompt version so prompt edits invalidate the cache.
- **Failure isolates to the candidate.** A single bad LLM response drops
  that candidate from the Judge queue with a log entry. The un-augmented
  anomaly ranking still populates the dashboard.
- **The Judge is behind a feature flag.** `LLM_JUDGE_ENABLED = True/False`
  at the top of the config. When off, the dashboard behaves exactly as
  today. A/B comparisons are one commit away.

## 6. Contract — data model in detail

### 6.1 Candidate context schema (input to LLM)

`docs/schemas/candidate_context.schema.json` — JSON Schema draft-2020-12,
validated with `jsonschema.Draft202012Validator`. See §4.2 for the shape.
`required`: `candidate_id`, `kind`, `features`, `ml_signals`.

### 6.2 Judge verdict schema (output from LLM)

`docs/schemas/judge_verdict.schema.json`. See §4.3.

Enum values are exhaustive — no free-text fields except `reasoning`. That
is the enforcement point for the "strict JSON" property.

### 6.3 Cache key

```
fingerprint = sha256(
    canonical_json(candidate_context) + prompt_version_string
).hexdigest()
```

`canonical_json` = sorted keys, no whitespace. `prompt_version_string`
is a semver-like string bumped on every prompt change (§7.2).

### 6.4 Analyst verdict log

`data/analyst_verdicts.jsonl` — one JSON object per line:

```json
{
  "ts": "2026-07-09T14:22:11Z",
  "candidate_id": "192.168.1.10",
  "pcap": "tcp_syn_scan.pcap",
  "prompt_version": "v1.0.0",
  "judge_verdict": {...},
  "analyst_verdict": "agree | disagree | override",
  "analyst_category": "port_scan | ...",
  "analyst_note": "free text"
}
```

Consumed by the calibration pipeline on the next run.

## 7. Architecture alternatives

Three viable shapes for the runtime. Comparison in §7.4, recommendation
in §7.5.

### 7.1 Alternative A — In-notebook synchronous cell

**Shape:** A new notebook cell (say `# ==== notebook cell 46 ====`) that
runs after the existing ML / rules / advanced cells. It:

1. Assembles candidates from the DataFrames already in the notebook's
   global namespace.
2. Calls the LLM client (synchronously, one request per candidate).
3. Writes verdicts back into a new `ip_agg["judge_verdict"]` column and
   a top-level `judge_summary` list.
4. Downstream Dash callbacks read those fields and render them.

**Pros:**

- Zero deployment complexity — the notebook already runs end-to-end when
  the user hits "Restart & Run All."
- Debuggable from Jupyter directly.
- No new processes, sockets, or files-in-flight.
- Consistent with the current notebook-as-app model (one file, one run).

**Cons:**

- Blocking. If the LLM API is slow or a candidate list is large, the
  dashboard load blocks on the whole Judge queue. A 30-candidate PCAP with
  a 2 s per-call API takes a minute to load.
- Notebook cells are hard to unit-test. Regression coverage lives in the
  extracted `run_pipeline.py` — which would need the same logic
  duplicated.
- The LLM API key lives in the notebook's execution environment, side by
  side with the user's `pip install` machinery.
- `app/dashboard_module.py` doubles in complexity to no benefit — the
  Judge cell is dead code for tests that don't set the API key.

### 7.2 Alternative B — Sidecar CLI + SQLite cache

**Shape:** A standalone Python module `app/llm_judge.py` (importable from
the notebook, from `run_pipeline.py`, and from a new CLI). It exposes:

```python
def judge_candidates(candidates: list[dict],
                    prompt_version: str = PROMPT_VERSION,
                    cache_db: str = "data/judge_cache.sqlite") -> list[dict]
```

The notebook cell shrinks to two lines:

```python
from llm_judge import judge_candidates
S["judge_verdicts"] = judge_candidates(assemble_candidates(S))
```

A new CLI `attack_tests/calibrate_judge.py` reuses the same function to
run the Judge over the five ground-truth PCAPs and compute kappa.

The SQLite cache is a single table:

```sql
CREATE TABLE judge_cache (
    fingerprint TEXT PRIMARY KEY,
    prompt_version TEXT NOT NULL,
    verdict_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    llm_model TEXT NOT NULL,
    latency_ms INTEGER
);
```

**Pros:**

- Testable in isolation — `test_llm_judge_unit.py` mocks the LLM client
  and asserts against fixture blobs; `test_judge_kappa_regression.py`
  runs against the real (or a recorded) LLM and asserts kappa >= threshold.
- Cache is durable across notebook restarts. Second run of the same PCAP
  hits the cache 100%.
- The calibration CLI is a natural side effect — same import, different
  entry point.
- Clean separation of concerns: notebook = orchestration + UI; module =
  Judge logic.
- Fits the repo's existing pattern: `run_pipeline.py` is exactly this
  shape for the ML layer.

**Cons:**

- Still blocking within a single notebook run (unless the module
  parallelizes internally with a thread pool — reasonable, easy).
- The notebook must import the module — one new top-of-notebook import to
  keep in sync when `dashboard_module.py` is regenerated.
- Adds `jsonschema` and a chosen LLM SDK to `requirements.txt`.

### 7.3 Alternative C — Persistent background service

**Shape:** A long-running FastAPI (or Flask) service, launched alongside
the Dash app, that owns:

- The LLM client.
- The SQLite cache.
- A `/judge` POST endpoint that accepts a candidate blob and returns a
  verdict.
- A `/kappa` GET endpoint that returns current live kappa for the Model
  Diagnostics pill.
- Optional: a worker thread that pre-warms verdicts for candidates
  streamed from the notebook via a queue.

The notebook calls the service over `http://localhost:PORT/judge`.

**Pros:**

- Best UX under load — the Dash app can render the queue as verdicts
  arrive rather than blocking on the whole batch.
- Live kappa endpoint is trivial. Model Diagnostics card polls it.
- The service can enforce a hard per-batch budget centrally (rate limit,
  token cap).
- Cleanest boundary for future extensions (multi-tenant, remote LLM
  backends, streaming responses).

**Cons:**

- Two processes to launch, health-check, and manage. The current "install
  Wireshark, run one notebook" story turns into "install Wireshark, run
  one notebook, and one service."
- Docker-ish deployment complexity leaks into a research project that
  today runs cleanly with `pip install -r requirements.txt` + Jupyter.
- The service is a new failure mode: if it crashes mid-batch, half the
  candidates have verdicts and half don't. Alternative B recovers
  transparently from the cache on the next run; Alternative C has to
  handle the mid-batch partial state itself.
- Overkill for the current single-analyst, single-machine use case.

### 7.4 Comparison

| Dimension | A: in-notebook | B: sidecar module | C: background service |
|---|---|---|---|
| Deployment complexity | lowest | low | high |
| Testability | poor (notebook-bound) | good (`pytest` friendly) | good, but needs process fixtures |
| Cache durability | in-memory only | persistent (SQLite) | persistent (SQLite) |
| Blocking behavior | blocks Dash load | blocks Dash load (thread-pooled) | non-blocking (async) |
| Latency to first verdict | ~1× LLM RTT | ~1× LLM RTT | ~1× LLM RTT (streaming possible) |
| Fits current repo shape | forced | natural (mirrors `run_pipeline.py`) | new pattern |
| Fault isolation | notebook crash = full loss | per-candidate isolation | per-request isolation |
| Live kappa pill | not straightforward | recomputed on Dash refresh | trivial endpoint |
| Cost to reverse | rewrite cell | delete module + revert cell | remove service + revert cell |
| CI wiring | duplicated logic | one import in test | needs service to spin up in CI |
| Extra dependencies | jsonschema, LLM SDK | jsonschema, LLM SDK | jsonschema, LLM SDK, FastAPI/Flask |

### 7.5 Recommendation

**Alternative B — Sidecar module + SQLite cache.**

Reasoning:

1. The repo's established pattern is exactly this: `run_pipeline.py`
   already lifts notebook cells into an importable module for tests and
   CLIs. Alternative B extends that pattern; Alternative A breaks it;
   Alternative C invents a new one.
2. Cohen's kappa calibration needs a batch runner over the five
   ground-truth PCAPs (`calibrate_judge.py`). Alternative B gets it for
   free by exposing `judge_candidates()` as a function. Alternative A
   forces the calibrator to reach into notebook globals or duplicate the
   logic. Alternative C forces the calibrator to spin up the service.
3. The dashboard's current concurrency model is single-threaded per Dash
   callback. The performance gap between B (thread-pooled batch) and C
   (async streaming) is real but not painful at the target scale (5–50
   candidates per typical PCAP).
4. Reversibility. Alternative B is one file (`app/llm_judge.py`) plus
   one import in the notebook. Turning off `LLM_JUDGE_ENABLED` reverts
   the visible behavior in a single commit. Alternative C leaves a service
   binary and health-check plumbing behind.

**Deferred to Alternative C only if:** live-recording mode (`tshark`
streaming) is extended to trigger Judge calls in real time, or the tool
grows from single-analyst to a shared SOC deployment. Neither is in scope
today.

## 8. Calibration pipeline

### 8.1 Ground-truth mapping

For each PCAP in `attack_tests/ground_truth.json`, build a truth set:

```
truth[pcap] = {
    ip: category
    for ip in (attacker_ips ∪ spoofed_ips ∪ reflector_ips)
}
```

Where `category` is derived from the `attack` field via the table in §4.4.
All other IPs seen in the PCAP that survive the candidate filter get
labeled `benign_anomaly` in the truth set — those are the false positives
the calibration must penalize.

### 8.2 Kappa computation

Cohen's kappa over a two-column matrix, one row per candidate:

```
              | truth = category
              +------------------
predicted     |
= category    |
```

Categories are the 7-way enum from §4.3. Multi-class kappa (weighted =
`"linear"` or unweighted) via
`sklearn.metrics.cohen_kappa_score(y_true, y_pred, labels=CATEGORIES)`.

Report both:

- **Verdict kappa** (3-way: `benign / suspicious / malicious`) — the
  coarse gauge.
- **Category kappa** (7-way) — the strict gauge.

The CI gate uses **category kappa**, threshold `0.65` (draft; see §8.4).

### 8.3 File — `attack_tests/calibrate_judge.py`

Shape:

```python
def calibrate(prompt_version: str, results_path: str) -> dict:
    """Run the Judge on every ground-truth PCAP, compute kappa, dump JSON."""
    y_true, y_pred = [], []
    per_pcap = {}
    for pcap, gt in GROUND_TRUTH.items():
        S = analyze_pcap(pcaps_dir / pcap, "S1")
        run_ml_on_session(S)
        findings = run_security_scans(S)
        candidates = assemble_candidates(S, findings)
        verdicts = judge_candidates(candidates, prompt_version=prompt_version)
        y_t, y_p = align_to_truth(candidates, verdicts, gt)
        per_pcap[pcap] = {
            "verdict_kappa": kappa_3way(y_t, y_p),
            "category_kappa": kappa_7way(y_t, y_p),
            "precision_by_cat": ...,
            "recall_by_cat": ...,
            "f1_by_cat": ...,
        }
        y_true.extend(y_t); y_pred.extend(y_p)
    overall = {
        "verdict_kappa": kappa_3way(y_true, y_pred),
        "category_kappa": kappa_7way(y_true, y_pred),
        "confusion_matrix": confusion(y_true, y_pred, CATEGORIES),
    }
    dump({"prompt_version": prompt_version, "overall": overall,
          "per_pcap": per_pcap}, results_path)
    return overall
```

Results written to `attack_tests/calibration/results/<prompt_version>.json`.

### 8.4 CI gate — `tests/test_judge_kappa_regression.py`

```python
def test_judge_category_kappa_meets_threshold():
    latest = load_latest_calibration_result()
    assert latest["overall"]["category_kappa"] >= KAPPA_THRESHOLD, \
        f"category kappa {latest['overall']['category_kappa']:.3f} "
        f"< threshold {KAPPA_THRESHOLD}"
```

`KAPPA_THRESHOLD = 0.65` initially. Raise to `0.70` after v1 stabilizes.

The test reads the already-produced calibration file — it does **not**
call the LLM. That keeps CI cheap and deterministic. The
production-of-results is a manual step tied to the prompt-iteration loop
(§10). This is a deliberate design choice: LLM-calling in CI is expensive
and non-deterministic; the guard is that a prompt change without a
matching calibration file is a merge-blocking gap the review will catch.

**Alternative gate:** re-run calibration in CI against a **recorded LLM
response** fixture (per prompt version). Same threshold, deterministic,
free. Pick this if the manual step feels too easy to skip.

### 8.5 Feedback loop

Every time the prompt changes:

1. Bump `PROMPT_VERSION`.
2. Run `python attack_tests/calibrate_judge.py`.
3. Compare kappa to the previous version.
4. **Commit only if kappa does not regress.**

`data/analyst_verdicts.jsonl` gets appended to the truth on the next
calibration run — analyst overrides become the growth path for the
ground-truth set.

## 9. Ensemble scoring

Priority score used to rank the queue the analyst sees:

```
priority(c) = w_anom * normalized_iso_score(c)
            + w_judge_conf * judge.confidence
            + w_cat * category_weight[judge.category]
            + w_ti * threat_intel_score(c)   # optional, 0 if none
```

Weights (initial draft):

| Weight | Value | Rationale |
|---|---:|---|
| `w_anom` | 0.20 | Retain the baseline detector as a floor |
| `w_judge_conf` | 0.40 | The Judge is the primary signal |
| `w_cat` | 0.30 | Category weight punishes benign_anomaly, rewards malicious cats |
| `w_ti` | 0.10 | Reserved for later threat-intel integration |

Category weights (initial draft):

```
category_weight = {
    "syn_flood":     1.0,
    "dns_amp":       1.0,
    "arp_mitm":      1.0,
    "port_scan":     0.8,
    "beaconing_c2":  0.9,
    "dns_tunnel":    0.9,
    "benign_anomaly": 0.0,
}
```

All weights are hyperparameters tuned once against the calibration set
(one-time grid search over the five PCAPs, maximizing precision@top-N).
They live in `app/llm_judge_config.py` and are surfaced in the Model
Diagnostics card.

## 10. Prompt design

### 10.1 System prompt (draft, English, embedded in `app/llm_judge.py`)

```
You are a network-security triage analyst. You receive a JSON blob
describing one candidate IP or flow that at least one unsupervised
detector or deterministic rule has flagged. Your job:

1. Return a strict JSON object matching the schema below. No prose
   outside the JSON. No markdown fences.
2. Assign a verdict (benign | suspicious | malicious) and a category
   from the fixed enum.
3. Ground every claim in the input blob — cite feature names in
   `evidence_features`.
4. If the signals are contradictory or thin, prefer "suspicious" over
   "malicious". If they are strong and unambiguous, use "malicious".
5. Never invent facts not in the blob. If a field is null, it is unknown,
   not zero.
6. `recommended_action` is a suggestion for a human, never an action
   this system will execute.

Schema:
{schema_here}

Category cheat sheet:
- port_scan: high unique_dsts + one dominant TCP flag counter + high
  ratio of that flag to total packets. Attackers touch many destinations.
- syn_flood: session-level SYN rate high AND many spoofed sources (see
  session_context and rule_signals.flood_alerts).
- arp_mitm: rule_signals.arp_multi_mac == true OR an IP appears in
  arp_spoofing_ips.
- dns_amp: rule_signals.amp_alerts non-empty AND UDP/53 responses
  dominate.
- beaconing_c2: advanced_signals.beaconing non-null and periodic.
- dns_tunnel: advanced_signals.dns_tunneling non-null OR unusually long
  DNS query strings.
- benign_anomaly: any statistical outlier without a matching attack
  pattern in the signals. Prefer this over "malicious" when in doubt.
```

Prompt versioning: `v0.1.0` for the first draft. Bumped by
`docs/PROMPT_CHANGELOG.md`.

### 10.2 User prompt

Just the candidate JSON blob (§4.2), verbatim, in a single message.

### 10.3 LLM configuration

- `response_format = json_object` (or provider-equivalent strict JSON).
- Temperature: `0.0` for reproducibility during calibration; `0.2` in
  production for slight variation on `reasoning`.
- Max output tokens: 400.
- Timeout: 15 s per request. On timeout, treat as a schema failure
  (retry once, then drop).

### 10.4 Provider selection

Not specified here. The `app/llm_judge.py` module exposes an
`LLMClient` protocol with a single method `judge(context: dict) -> dict`.
Concrete implementations for each provider live in
`app/llm_clients/`. The active provider is chosen by
`LLM_JUDGE_PROVIDER` in config. This keeps the switch to a different
provider (or an on-prem model via Ollama) mechanical.

## 14. Rollout plan

Ordered phases. Each is an independent commit / PR.

1. **Fix known DBSCAN / `eps_auto` edge-case bugs** (baseline stability
   prerequisite — the Judge inherits every input the baseline produces).
   This is scope defensive; skip only if the current CI is green against
   the five ground-truth PCAPs and there are no open issues in that area.
2. **Land schemas + config skeleton.** `docs/schemas/*`,
   `app/llm_judge_config.py`, `data/` in `.gitignore`. No behavior change.
3. **Land `app/llm_judge.py` behind the feature flag, flag off by
   default.** Includes `assemble_candidates()`, `LLMClient` protocol, one
   concrete provider, cache, retry/drop.
4. **Land `attack_tests/calibrate_judge.py`** and commit the first
   calibration result at `attack_tests/calibration/results/v0.1.0.json`.
   Report kappa in the PR description.
5. **Land `tests/test_judge_kappa_regression.py`.** Threshold at 0.60
   initially (below the v0.1.0 measured value, whatever that is), to give
   headroom for the first few prompt iterations without immediately
   blocking merges. Raise to 0.65 after two successful prompt iterations.
6. **Land dashboard cell + UI card + verdict log widget.** Flag stays
   off in `main`; developers flip it locally.
7. **Flip the flag on** once category kappa >= 0.65 on the calibration
   set and unit tests pass.

Iteration loop from step 3 onward:

```
prompt edit -> bump PROMPT_VERSION
            -> run calibrate_judge
            -> compare kappa vs previous
            -> commit if kappa did not regress
            -> update docs/PROMPT_CHANGELOG.md
```

## 15. Metrics

Recorded on every calibration run and every live session.

| Metric | Where | Target |
|---|---|---|
| Category kappa (calibration) | `attack_tests/calibration/results/<v>.json` | >= 0.70 |
| Category kappa (live rolling 7d) | Model Diagnostics pill | >= 0.60 |
| Precision @ top-50 vs anomaly-only | offline eval | +25 pp |
| FP-burn rate (candidates the analyst rejects per hour) | analyst verdict log | −50% |
| LLM latency p50 / p95 | cache DB | tracked, no hard SLA |
| LLM cost per candidate (tokens × price) | cache DB | tracked, hard cap `MAX_TOKENS_PER_BATCH` |
| Analyst agreement rate | live verdict log | 60–85% (bounds — see below) |
| Per-category confusion matrix (rolling) | calibration + live | off-diagonal < 15% per cell |

**Analyst agreement bounds:** below 60% signals prompt drift → recalibrate.
Above 85% signals rubber-stamping → sample 5% of verdicts weekly for
audit.

## 16. Scope boundaries

- The Judge is triage. It does not act. `recommended_action: "block"` is
  a suggestion, never wired to a blocklist or firewall.
- Live-recording mode (`tshark` streaming) is out of scope for v1. The
  Judge only runs at PCAP load time. Alternative C (§7.3) is the door back
  in.
- Beaconing and DNS-tunnel categories are declared in the enum but not
  yet in ground truth. Their calibration is measured only against
  synthetic or future-added PCAPs; kappa is computed only over the
  categories with truth coverage until then.
- Judge is single-tenant. No multi-user auth on the widget. Analyst
  verdicts are appended to a local file; a future SOC deployment needs a
  proper store.

## 17. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Prompt drift silently regresses kappa | CI gate on category kappa; `docs/PROMPT_CHANGELOG.md` records kappa per version |
| LLM API outage blocks dashboard load | Feature flag + cache — a fully warm cache serves without the API |
| LLM emits invalid JSON | Schema validation + one retry + drop + log |
| Cost blows up on a large PCAP | Hard `MAX_CANDIDATES_PER_BATCH` cap; log dropped candidates |
| Analyst rubber-stamps verdicts | 5% weekly random-sample audit; disagreement-rate metric |
| Ground-truth set is small (five PCAPs) | Analyst verdict log extends the truth set over time; declare it explicitly as a known limitation until beaconing / tunnel PCAPs are added |
| Cache poisoning by an invalid response getting written | Only schema-validated verdicts are written to cache |
| Non-determinism in reasoning trace breaks tests | Tests assert only on structured fields (verdict, category, confidence), never on the reasoning string |

## 18. Open questions

Left for the implementer:

1. **Provider choice.** The spec is provider-agnostic. Which model? On-prem
   Ollama? SaaS API? The `LLMClient` protocol admits either — but the
   default provider committed to `requirements.txt` needs a call.
2. **Enrichment sources.** `enrichments.reverse_dns` and
   `enrichments.asn` are declared. Do they get populated from a local
   MaxMind DB, a live lookup, or left null in v1?
3. **Prompt language.** English by default; a Hebrew prompt variant is
   feasible but adds one axis of drift. Recommend English only for v1.
4. **Kappa weighting.** Unweighted vs linear-weighted. Linear kappa is
   more forgiving for near-miss categories (`syn_flood` predicted as
   `port_scan` is less bad than as `benign`). Recommend linear.
5. **CI cost model.** Manual calibration + recorded fixture (§8.4
   alternative gate) vs a real LLM call in nightly CI only. Recommend
   manual + fixture until cost is a demonstrated non-issue.

## 19. Success definition

v1 is done when all of the following hold:

- `LLM_JUDGE_ENABLED = True` in `main`.
- Category kappa on the calibration set >= 0.65.
- `tests/test_judge_kappa_regression.py` guards `main`.
- The dashboard's re-ranked queue card is visible on both S1 and S2 loads.
- The Model Diagnostics card shows a live kappa pill.
- `docs/PROMPT_CHANGELOG.md` has at least one entry.
- Category kappa on the calibration set has not regressed across the
  last three commits.

v1 is explicitly **not** required to:

- Cover `beaconing_c2` or `dns_tunnel` on labeled data.
- Support live-recording mode.
- Auto-block anything.
